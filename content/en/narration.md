Every project moves along two lines at once. One is our understanding of the problem: what we are trying to solve, and what would count as solving it. The other is the answer that code, data and real use keep sending back. Understanding changes, tools are replaced, and people and AI agents take turns carrying the work. When the two lines drift apart, effort stops adding up, and whoever picks the work up next has to start by guessing. ETHOS is designed for this situation, where people and agents share the work on a repository. The name stands for Evidence-grounded Trust for Human-Agent Operational Stewardship. It promises three things, rather than more governance: accepted intent is not lost, uncertainty is stated so that someone can act on it, and results can be recovered when something goes wrong. That is what ETHOS aims for, and its own documents say that the whole promise cannot yet be counted as delivered.

Take two familiar pieces of work. One improves a market-data pipeline: the data must be complete, and running the same batch twice must not leave duplicate records. The other studies a stock-selection signal: was every piece of information the backtest uses actually available at the moment of each decision, and does the result survive a different period? Both can use the same tools, yet they are judged by entirely different standards, and those standards belong to the project. ETHOS does not decide what good data or a valid signal is. It ties together how intent is set, how people and agents collaborate, how results are verified and how things change when they must, so that the project can judge by its own standards. These two examples run through the rest of the film; they only illustrate the ideas, and are not measured results.

Working together starts with saying what will change, and how we will know the change worked. For a pipeline that must tolerate reruns, writing "more reliable" is not enough. We also have to write down which records count as the same record, which look-alike records must still be kept, and how we will verify that nothing is duplicated. A signal study needs its hypothesis written down, together with the result that would refute it. All of this goes into an official Change in the repository: a set of documents written with OpenSpec, an existing specification tool. A proposal says why, specs state the required behavior and its acceptance scenarios, a design records the trade-offs, and a task list records progress. ETHOS reads the Change and compiles it into acceptance criteria. In the repository, accepted intent is kept in the Change and nowhere else. Research may push the intent to change, but a revised requirement has to be accepted again by whoever has the authority to decide.

Understanding a requirement and turning it into checks are two different jobs. Understanding takes judgment. Every relevant constraint in the declared sources is kept, excluded by an authorized decision, or marked as unresolved. Examples and counterexamples both challenge that understanding, including what is out of scope and where the exceptions lie. Only then does ETHOS deterministically compile the accepted intent into acceptance criteria and checks. The same inputs always compile to the same acceptance criteria, but that cannot certify that anyone understood correctly. Transcripts, an agent's memory and summaries are leads, not authority, and repeating a request does not make it binding. Each obligation, meaning each distinct thing that must be accounted for, is given exactly one disposition: accepted, superseded by a later governing instruction on the same subject, pending verification, or rejected with its reason.

Once a requirement is clear, it has to mean the same thing everywhere. How a duplicate record is recognized should be defined by the one module responsible for that meaning; the interfaces, tests and documentation follow from it, instead of each keeping its own version. ETHOS calls this giving every obligation exactly one owner. The same principle applies to tools. Supporting work goes first to what already exists: official standards and tools such as OpenSpec and Git, the platform's own capabilities, and mature tools. Custom supporting code is written only where a real gap has been shown, its job is bounded, and its net benefit is clear. When a replacement is chosen, the path it replaces is removed in the same step, rather than both living on. ETHOS focuses its own code on one job: turning accepted intent and freshly observed facts into verifiable changes to the repository.

A Change is often carried by several people and agents at once. Everyone needs to know who owns which part, what is still an experiment, and how the work is handed over. ETHOS organizes this with Work Lanes. Each lane has its own Git worktree, a separate working copy of the files, so everyone can change things separately, then review the changes and combine them. Who holds a lane right now is coordinated by an expiring Lease, which records only four things: the lane, its holder, its expiry time, and a generation number that tells one turn from the next. Everything else is observed afresh. Lanes can cooperate, combining several contributions; they can compete, with one result chosen, or none. Even when an exploration ends with only a negative result, the useful evidence is kept rather than deleted along with the lane.

Holding a lane is not permission to edit a particular file at this moment. Before each change to a tracked file, the current state of the lane's worktree and of exactly the files about to change is checked again, in a separate check just before writing. If there is uncommitted work there, if the files belong to someone else or their ownership is unclear, or if the state is not what was expected, the files can be read but not written until a fresh check clears the write. A check that passed a few minutes ago does not stand in for one now. Only writes to those files wait; unrelated work carries on. There is one limit: lanes and checks coordinate only participants who follow the protocol. It is not isolation of the kind an operating system provides, and it cannot stop an uncooperative program running under the same account.

All of this rests on a small trust kernel. What it does fits in one sentence: from accepted intent, freshly observed facts and earlier verification records, it compiles one plan, carries it out, and writes new ones. Accepted intent comes from the official Change, and the kernel compiles its acceptance criteria into a transient value called the Commitment. The fresh observations are the Facts, and the compiled plan is the TransitionPlan. All three are temporary: they serve one decision and are then discarded. Of the kernel's values, the only one that persists is the Attestation, a record of what was observed, judged, proved or done, which verifier produced it, and within which limits its conclusion holds.

A plan does not take effect on its own. Git points at versions through names called references. When a plan updates a reference, the kernel checks once more that its old value is the one it expected, and only then writes the new value. Checking and writing are a single step that cannot be interrupted, called compare-and-swap. If the old value has changed, the plan is discarded, and a new one has to be compiled from fresh facts. After the write, the result is read back to confirm what actually happened. The kernel stops when a required fact is unknown, when it is unclear who has the authority to decide, when something it relied on is out of date, or when inputs contradict each other. When it stops, it names what happened, why it stopped, the evidence or the missing fact, the one safe next action, and whether a person has to decide. In daily use you start with the ETHOS status command, see where things stand and what comes next, take only that action, and then look again.

Verification has to state what was checked: which commit, with exactly what code, against which requirement, by which verifier, where and under which rules. ETHOS runs a repository's declared checks locally as a proof. That local proof, the automatic checks on GitLab and those on GitHub are three separate sources of evidence. So are the author's identity, the commit's signature, the released files and the installed program. A pass on one never implies a pass on another. That is why anyone who says something is done has to name exactly which of these were verified this time. If the local proof has passed but the results on the hosting platforms have not been read, the honest statement is that the local proof passed and the hosted results are not yet verified.

Review does not have to wait for proofs to finish. It looks at one exact commit and the new commits it brings in. Lanes can combine their work on a candidate branch, a local branch kept for bringing work together. Or one exact commit can be put forward for review on its own. ETHOS protects only two branches, usually called dev, which holds accepted work, and main, which carries releases. Someone without write access to them proposes a change through a merge request, and a maintainer may then accept the reviewed commit after checking it again. Work that has not been accepted yet is judged by the rules that were already trusted; a proposal that changes the rules cannot approve itself. Continuous integration, the service that runs checks on every push, works independently and observes without holding a lease or any authority.

Accepting code, cutting a release and putting it in users' hands are three separate steps. For a release, the commit and the tag are created in local Git first. Every declared platform, such as GitLab and GitHub, receives the same commit and the same tag; none copies from another, and none may rebuild or re-sign them. A push that succeeds on one platform says nothing about another. A platform that is temporarily behind, within the declared time window, is pending; past that window, a difference counts as divergence. The official Change also keeps track of what is still owed: accepted code does not mean delivery is finished. It still has to be confirmed where the version was deployed and which version users are actually running.

Now back to the two examples from the start: the market-data pipeline and the stock-selection signal. Suppose the checks pass and the version is deployed. Is any market data missing? After a rerun, are any records duplicated? Only real use can answer those questions. What the result can show depends on which version ran, in what environment, against which baseline, and over what observation window. A successful deployment and passing checks are only intermediate claims. The signal study, too, has to keep asking: was the information the backtest used really available at the time, does the result rest on one stretch of the sample, and where does uncertainty remain? A historical backtest cannot prove future trading returns. ETHOS is designed to connect these observations back to the original requirements and hypotheses, without letting development metrics stand in for the project's own measure of business success.

Feedback is not always a single fix. It can correct how something is used, call for a different method, shake the concepts and structures the work uses to express meaning, or change how we understand the purpose and the assumptions behind it. When evidence challenges an understanding at a higher layer, the corrected meaning has to be recompiled through every layer that depends on it. A revised goal or standard has to be accepted again by whoever has the authority; quietly loosening a condition so that a result passes is not allowed. The feedback mechanism itself stays open to correction. To call a round of feedback closed, technical verification, delivery and business results each need their own evidence. One project's experience can suggest improvements to shared mechanisms, but the suggestion does not carry that project's authority or private business context with it.

Sometimes a new situation simply cannot be reconciled with the current model. Model here means the concepts and structures the work uses to express meaning, not a statistical model. Two valid inputs may contradict each other, or the current model cannot represent the situation without losing information. By design, ETHOS then reports that Model Promotion is required, and every change to the repository that depends on the unresolved meaning is blocked until Model Promotion is done, while unrelated work continues. Model Promotion means keeping the conflicting cases and their evidence, finding the smallest part of the model that is affected, and changing it so that it can hold them. After that, the plans that depend on it and the views derived from it are recompiled, the new model is verified to cover every case, and what is left of the old form is absorbed or retired. No exception, alias, fallback or compatibility shim is added to work around the problem, and no parallel source of truth is set up.

ETHOS governs its own product repository with the same kernel and the same procedure it applies to the repositories that adopt it. That is what isomorphic governance means. The difference lies only in profiles and adapters: each repository declares its checks, parameters and depth of proof in its own profile, and adapters connect native tools such as Git, the code-hosting platform and continuous integration. This does not turn each repository into a copy of ETHOS. Each repository keeps its own domain model, layout and platform conventions, and ETHOS judges each change through the same evidence-grounded loop. The first hour with ETHOS deliberately asks for very little. In a repository, run the ETHOS status command to see the current facts, the gaps and the next action. For a repository that has not yet adopted ETHOS, preview the adoption plan first; the preview changes nothing. Apply it only when it shows no conflicts and you know how to recover, because if applying it is interrupted, the change can be left half done.

A project can take on the structure it needs a little at a time, adjust it to its own work, and be handed over to another person or agent; by design, it can also leave ETHOS altogether. Adoption is designed to be previewable, to give the same result when repeated, to change as little as it can, and to be reversible until ETHOS makes its first change under governance. Uninstalling is designed to be clean, leaving no hook scripts that run automatically, no generated file acting as a source of truth, and no second control system. Before a handoff or an exit, ownership must pass to whoever takes over, and useful results and necessary evidence must go to their owner or be kept in a form that can be recovered. After that, a mechanism whose obligation is done should be retired, so that it does not become a new burden.

Back to the two lines we began with. Understanding gives action its direction, and real outcomes come back to correct the understanding. The design of ETHOS holds to four plain rules of judgment. Preserve meaning with the smallest model that is enough, and make a distinction only where it changes what we do. Keep authority separate from views, because seeing is not permission. And retire a mechanism when its obligation is gone. Done this way, the pipeline would leave an improvement that can be verified, and the research would leave its conditions on record for the next study to question. When a new problem arrives, what was understood and what was learned are still a place to start. The project can keep going, and the method stays open to change.
