An Agent hands back one sentence: "Done. All tests pass." How much does that sentence tell you? Which commit is it talking about? Which tests ran, and where? Is what it built the thing that was really asked for? And if it got something wrong, can you get back to where you were? More and more of our code is now changed by interchangeable Agents: when one session ends, another picks up the work. Writing code keeps getting easier. Knowing whether you can rely on it does not. ETHOS is built for that problem. We will look first at why it is hard, then at what ETHOS is and why it is designed the way it is, and finally follow one requirement from start to finish.

It is hard in three ways. The first is that meaning drifts. Not long ago, one person often carried a piece of work from start to finish, and the whole story lived in that one head. Now a request passes through interpretation, retelling and handoffs on its way to delivery, and through several people and several Agents. At every handoff a summary takes the place of the words before it, and when a session ends, any constraint that was never written down ends with it. A specification can be complete and well formed and still be aimed at the wrong goal. The second is that claims go beyond their evidence. A run that passed on one machine becomes "everything passes". A merge is taken for a release, and a deployment for actual benefit. Each of these steps proves only its own part. The third is that changes are made before the facts are checked. Two Agents work on the same branch; one writes from an outdated memory, and the other one's work is overwritten. The same version is pushed to two code-hosting platforms, GitLab and GitHub. It succeeds on one and fails on the other, and nobody can say what state things are in. Simply trying again does not settle it. The usual answer is more process: another register, another ledger, another copy of the same rule. Each of these needs someone to keep it up. Over time they go stale and contradict each other, and they turn into a burden of their own.

ETHOS takes a different path. Its name stands for Evidence-grounded Trust for Human-Agent Operational Stewardship. It aims to give people and interchangeable Agents one reliable path: from understanding a problem, to changing a repository, to seeing how that work turns out once it is in use. It promises three things: meaning is kept; uncertainty is stated plainly, so that someone can act on it; and when something goes wrong, the result can be recovered. More governance is not one of its promises. A small trust kernel holds that path up. It takes three inputs: the intent that has been accepted, the fresh facts it observes right now, and the attestations already on record. From these, by fixed rules, it compiles a plan. At the moment it writes, the kernel checks again. Then it records what it observed, what it decided and what it did, as new attestations. These things last for different lengths of time. Intent lives in one official Change, a written record kept in the repository, and the kernel compiles it afresh from there each time it needs it. Facts are observed again every time and never stored away as truth, because they can change at any moment. A plan is either carried out or discarded, and never kept; it can always be compiled again. The kernel keeps only one thing for the long term: the attestation. Every attestation names who verified it and where it holds. ETHOS does not take over the systems you already have: the model that describes your business, the service that runs your automated checks, the apps your Agents run in, your issue tracker. They stay what they are. What every repository shares, ETHOS owns once, so that each repository carries only its own purpose. These are ETHOS's design aims. Its own documents say plainly that the kernel alone does not prove the whole path has been delivered.

So why is ETHOS designed this way? Its Product Design Contract sets out four rules of judgment, and one example can carry all four. The example is made up to show the idea; it is not a measured case. There is a market-data pipeline that can be run again whenever it is needed. A researcher asks for one thing: running the same batch again must not add duplicate records, but any value the vendor has corrected must stay. After two handoffs, an Agent's summary has shrunk to a single line: "Deduplicate by stock code and date." Followed to the letter, that line would delete exactly the corrections that had to stay. The summary made reading faster. The trouble starts when it takes the place of the original words and no one goes back to them. Rule one: preserve meaning with the smallest model that is enough. Here, a model means the concepts and structure that express the meaning. The intent goes into one official Change, and only there: what is to be solved, why, and what counts as solved. Then examples of both kinds test how it has been understood. An exact repeat goes. A correction to the same stock on the same day stays. "Deduplicate by stock code and date" fails that second example, and the corrections are saved. The interpretation always stays open to challenge. Only what a person has confirmed and accepted is compiled into checks, by fixed rules. Compiling guarantees that the same input always yields the same checks; it cannot prove that the understanding behind them is right. That is why conversations, memories and summaries are only leads.

Now back to that sentence, "All tests pass." By ETHOS's rules, that sentence has to be taken apart. The local proof, the full set of checks run on this one commit, has passed, so the work may move forward locally. The automated checks on GitLab and GitHub have no result yet. Nothing has been released. No one is using it. And as for actual benefit, there is no observation at all. That is rule two: distinguish only what changes action. These are separate planes of evidence: each one, once it passes, permits a different next step. One of them passing never means another has passed. So whenever someone says "done", they need to say which of these were verified this time. A judgment, too, has only three outcomes: pass, block and unknown. Missing or unverifiable required facts make it unknown; a conflict or an explicit failure makes it block. Only pass permits action, and unknown is never permission. And a distinction that would not change any action is never added.

Back to the example. A second Agent is at work at the same time. It remembers the branch sitting at yesterday's commit, and its dashboard is all green. But between compiling a plan and writing, someone else may have changed things. At the very moment it is about to write, ETHOS checks again, and the branch has moved on. The target is no longer what the plan expected, so nothing is written, and the plan is compiled again from fresh facts. Checking and writing happen as one step, and afterwards the result is read back to confirm what happened. When a version is pushed to several platforms, which succeeded, which failed and which are still pending are all recorded as they are. ETHOS never claims that several platforms succeed or fail together. That is rule three: keep authority separate from views. In ETHOS, authority means what a judgment may rest on: the user's current instruction, what the repository actually contains, the accepted Change, fresh facts, the applicable policy, and the attestations that are still valid. Summaries, dashboards, status output and an Agent's report are views, like that green dashboard. They are derived from that authority so that people can read it. A view helps people see, but it never counts as authority. When authority is ambiguous, or a condition has gone stale, the judgment cannot pass.

In the example, the first Agent wrote a temporary deduplication script and kept a progress sheet of its own. Once the repository's own declared check carries the obligation to deduplicate, and the official Change's task list carries the progress, the script and the sheet are retired, not kept "just in case". That is rule four: retire a mechanism when its obligation disappears. Every obligation has exactly one owner. An obligation that is the same for every repository belongs to ETHOS; each repository declares only the checks that are its own. ETHOS judges its own repository by the same obligations it ships to every other one. A replacement may never be weaker than what it replaces. And a Change closes on what it actually delivered: unfinished work stays on the record instead of passing for done. Every mechanism needs someone to maintain it and explain it, and in time it goes stale. Keep the ones whose obligation is gone, and governance itself becomes the burden.

Now follow this requirement through its whole life. The researcher's request is first written into an official Change. The work is done in a Work Lane of its own, and who holds that lane, and until when, is on record. Before any file under version control is edited, ETHOS checks once more, against the state at that moment, whether the write may go ahead. Halfway through, one Agent's session ends. ETHOS is designed so that the Agent that takes over does not rely on the last one's memory. It continues from the Change and the attestations already in the repository, and from fresh facts. When the work is finished, a full local proof runs on that exact commit and leaves an attestation behind. A maintainer reviews and authorizes the work, and only then is it accepted into the protected development branch. After that, it is published to each platform, and each platform's result is confirmed on its own. Once the version is live, whether it works, and whether it brings any actual benefit, only shows in real use. From here on, the story follows a stretch of the path that ETHOS is designed for; its own documents say that this stretch, like the handover between Agents, has not yet completed acceptance. A few days later, the vendor issues two corrections for the same stock on the same day. The pipeline only knows an original value and a single correction, so the second correction overwrites the first. The people watching the pipeline report this back, and ETHOS requires that three things be judged separately. The observation is that the first correction has disappeared. The inference is that the vendor can correct a value more than once. And the proposed remedy is to tell records apart by the revision number the vendor supplies. A failed implementation does not by itself mean the model is wrong, and the two have to be told apart first. This time the fault is in the model: the idea of "the same record" is missing a dimension. So a new official Change revises the model at the smallest boundary the problem touches, and every check that depends on it is compiled again. No exception or side path is added to work around the model, and no second source of truth is set up. The goal, no duplicate records, is not relaxed in the slightest. A goal or a standard changes only through authorized intent alignment, that is, an explicit, authorized decision to realign the intent. It is never silently loosened so that a result can pass.

So, back to where we began: "Done. All tests pass." Whether that sentence can be trusted does not depend on who said it, or on how much process stood behind it. It depends on whether the meaning can be found in one place, whether the claim stays within its evidence, and whether you can get back after a mistake. That is what the ETHOS mark draws. One origin: a question bounded before it becomes a change. Two passages: distinctions made only where they decide action. One boundary: evidence and claims each keeping to their scope. And the single cinnabar-red point is where a claim must be bound to its evidence.
