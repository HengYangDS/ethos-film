做一个项目，总有两条线在同时往前走。一条是我们对问题的理解，也就是要解决什么，做到什么程度才算解决。另一条，是代码、数据和实际使用一次次给出的答案。理解会变，工具会换，人和 AI 智能体，也就是 Agent，会轮流接手。两条线一旦对不上，做过的工作就积累不起来，后来接手的人只能从头去猜。ETHOS 这个名字取自几个英文词的首字母，合起来的意思是，人和 Agent 一起打理一项工作时，信任要建立在证据上。它不是要多加一层治理。它承诺三件事。一是已经采纳的意图不会丢。二是不确定的地方会明确说出来，好让人能接着处理。三是出了错能恢复过来。这些是 ETHOS 要达到的目标。它自己的文档也写明了，眼下还不能说这些承诺已经全部兑现。

先看两件大家都熟悉的工作。一件是改进一条行情数据管线，要求数据完整，同一批数据重新跑一遍，也不能多出重复的记录。另一件是研究一个选股信号。要追问的是，回测里用到的每一条信息，在当时做决策的时候，真的已经拿得到吗？换一段时间，结论还站得住吗？这两件事可以用同一套工具，判断成败的标准却完全不同，这些标准由项目自己来定。什么是好的数据，什么是有效的信号，ETHOS 不替项目回答。它帮项目理顺几件事：意图怎么定，大家怎么协作，结果怎么检验，要改的时候怎么改，好让项目按自己的标准来判断。后面就拿这两个例子来讲。它们只是举例，不是实测的结果。

一起做事，先要说清楚打算改什么，又凭什么判断改得有效。比如管线要能重新运行，光写一句“更可靠”是不够的。还要写明哪些记录算同一条，哪些看着像重复、其实要留下，以及用什么办法检验确实没有重复。研究信号，也要先写下假设，再写明出现什么结果就说明它不成立。这些内容，都写进仓库里的一份正式变更。正式变更用现成的规格工具 OpenSpec 来写，分成几部分：提案讲为什么要改，规格写清要满足的行为和验收场景，设计记下做了哪些取舍，任务清单记录进度。ETHOS 会读取并编译这份变更。在仓库里，采纳了的意图只记在正式变更里，不在别的地方另记一份。研究有了新发现，意图也可能跟着改。但改过的要求，要由有权决定的人重新采纳。

读懂一项需求，和把它变成检查，是两回事。读懂要靠判断。在指定范围的资料里，每一条相关的约束，要么留下，要么经过授权排除，要么明确标成还没解决。再用正例和反例去考这个理解，哪些不做、例外在哪里，都要考到。这之后，ETHOS 才按固定的规则，把已经采纳的含义编译成验收条件和检查。同样的输入，总会编译出同样的验收条件，可这保证不了理解本身是对的。对话记录、Agent 的记忆、各种总结，都只是线索，没有决定权。一条要求说上很多遍，也不会因此就算数。每一项责任，也就是每件需要有个交代的事，最后都要有一个去向，而且只能有一个：采纳、被后来针对同一件事的指示取代、等待检验，或者拒绝并写明理由。

要求明确以后，还要保证它在哪里都是同一个意思。比如“重复记录”怎么认定，只该由专门负责它的那一个模块来定义。接口、测试和文档都照着它来，不各写一套。ETHOS 管这叫：每一项责任，只交给一个地方负责。用工具也是同样的道理。辅助的工作，先交给官方的规范和工具，比如 OpenSpec 和 Git，还有平台自带的功能和成熟的工具。只有证明现成的办法确实缺了什么，要写的代码边界清楚，净收益也说得清，才自己写辅助代码。选定了新办法，就把它替下来的旧做法一并撤掉，不让两套东西长期并存。ETHOS 自己的代码集中做一件事，就是把采纳了的意图和刚观察到的事实，变成可以检验的仓库改动。

一项正式变更，常常有好几个人和 Agent 同时在推进。谁负责哪一块，哪些还只是尝试，工作怎么交接，大家心里都要有数。ETHOS 的办法是工作通道，英文叫 Work Lane。每条通道有一份自己的 Git 工作区，也就是单独的一整套项目文件。大家先各改各的，再审阅、集成。一条通道此刻归谁，靠一份会到期的租约来协调，英文叫 Lease。租约只记四样东西：哪条通道，谁持有，什么时候到期，还有一个编号，用来分清这是第几次持有。别的情况，每次都重新去查。几条通道可以合作，把各自的贡献合到一起；也可以竞争，最后选出一个结果，或者一个都不选。就算一次探索只留下否定的结论，有用的证据也要保留，不能跟着通道一起删掉。

持有一条工作通道，不等于此刻就能改某个文件。每次修改受版本管理的文件之前，都要按当时的状态，再核对一次这个工作区、这几个文件能不能写。这是写入前单独的一道检查。如果那里有别人还没提交的改动，或者归属说不清，或者状态跟预期对不上，就只能看、不能写，直到重新检查放行。几分钟前通过的检查，代替不了现在再查一次。无关的工作可以照常继续。还有一个限度要说清楚。这套机制协调的，是愿意遵守约定的参与者。它不是操作系统那种隔离，拦不住同一个账户下不守约定的程序。

这套做法靠一个很小的信任内核来支撑。内核做的事，一句话就能说完。它拿已经采纳的意图、刚观察到的事实和以前留下的核验记录，编译出一份计划，执行这份计划，再写下新的核验记录。采纳的意图来自正式变更，内核把其中的验收条件编译成一个临时的值，叫 Commitment。刚观察到的情况叫 Facts，编译出来的计划叫 TransitionPlan。这三样都是临时的，只在这一次判断里用，用完就丢。真正留下来的只有核验记录，英文叫 Attestation。它记下一次观察、一项判断或者一次改动，并写明出自哪个检验程序、结论在什么范围内成立。

计划不会自己生效。Git 用一个个名字指向各个版本，这些名字叫引用。计划真要改动一个引用的那一刻，内核会再核对一次旧值，确认还是预期的那个，才写入新值。核对和写入是一步完成的，中间不能被打断，这叫 compare-and-swap。旧值要是已经变了，原来的计划就作废，要按新的事实重新编译。写完以后，还要把结果读回来，确认实际发生了什么。有几种情况，内核会停下来：必需的事实还不知道，谁有权决定说不清，它依赖的条件已经过时，或者输入之间互相矛盾。停下来的时候，它会讲明出了什么事、为什么停、证据是什么或者还缺哪个事实。它还会给出唯一安全的下一步，并说明要不要人来决定。平时用的时候，先运行 ethos status，看清现状和下一步，再动手。

检验的时候，也要说清楚查的是什么：哪一次提交里的哪一份代码，依据的是哪一项要求，用的是哪个检验程序，在什么条件下通过。在本地跑的证明，GitLab 上的自动检查，GitHub 上的自动检查，是三份来源不同的证据。作者身份、提交签名、发布出去的文件、装好的程序，也各是一份独立的证据。一份通过了，推不出另一份也通过。所以，说一件事做完了，要讲明这一次实际检验了哪几样。比如本地证明通过了，GitLab 和 GitHub 上的结果还没看，那如实的说法是：本地证明通过，两个平台上的结果还没有检验。

审阅不用等所有证明都跑完。它看的是一个具体的对象，以及这次带进来的那几次提交。几条通道的改动，可以先合到本地一条专门做集成的分支上，这叫候选分支。也可以把某一次提交单独拿出来，交给审阅者看。ETHOS 只保护两个分支：dev 存放已经接受的改动，main 用来发布。对这两个分支没有写入权限的人，可以通过合并请求提出改动；维护者重新核对之后，可以接受审阅过的那次提交。一项改动还没被接受，就用之前已经信任的规则来判断它。修改规则的提案，不能自己给自己盖章。每次推送代码，持续集成服务都会自动跑一遍检查。它独立运行，观察结果，但不持有租约，也没有决定权。

代码被接受，做成发布版本，再真正交到使用者手里，这是三个不同的步骤。发布时，提交、标签这些对象都先在本地 Git 里定下来。GitLab 和 GitHub 收到的是同一次提交、同一个标签，两个平台谁也不从对方那里拷贝，也都不能重新构建或者重新签名。推到其中一个平台成功了，不代表另一个也成功。某个平台落后，只要还在设定的时间窗口内，就算待同步；过了这个窗口还不一致，才算分歧。正式变更也要记下没完成的责任。代码合进去了，不等于交付完成了。还要有人确认，版本部署到了哪里，使用者实际在用的又是哪个版本。

现在回到管线和信号。假设检查都通过了，版本也部署了，行情数据有没有漏？重新跑过以后，有没有留下多余的记录？这些问题，要到实际环境里去找答案。这次的结论能说明什么，要看用的是哪个版本，在什么环境里跑，跟什么基线比，观察的是哪段时间。部署成功、检查通过，都只是中间的结论。信号研究也一样，还要接着问：回测用到的信息，当时真的能知道吗？结论是不是只靠某一段样本？哪些地方还不确定？历史回测证明不了将来的交易收益。按设计，ETHOS 要把这些观察跟原来的要求和假设对应起来，但不会拿开发上的指标，去代替项目自己衡量业务成败的标准。

反馈不一定只是修好一个错误。它可能纠正实际的用法，可能要求换一种做法，可能动摇用来表达含义的那套概念和结构，甚至让人重新理解目的本身。更高一层的理解一旦被证据动摇，修正后的含义，就要顺着依赖它的各层重新编译。改目标、改标准，都要由有权决定的人重新采纳。不能为了让结果通过检查，悄悄把条件放宽。反馈机制本身，也始终可以修正。技术上的检验、交付和业务上的结果，各自要有各自的证据。一个项目的经验，可以拿来提议改进大家共用的机制；但这个项目的决定权和私有的业务背景，不会跟着这条建议一起交出去。

有时候，新的情况跟现有的模型怎么也对不上。这里说的模型，就是前面讲的概念和结构，不是统计模型。可能是两份都有效的输入互相矛盾，也可能是用现有的模型去表达，总要丢掉一些信息。按设计，这时 ETHOS 会报告需要做模型提升，英文是 Model Promotion。依赖这层含义的改动也会先停下，等模型提升做完；跟它无关的工作照常进行。模型提升的做法是这样的：先留住那些互相冲突的例子和证据，找到模型里受影响的最小部分，把它改到能装下这些情况。然后重新编译依赖它的计划和视图，检验一遍覆盖是否完整，再把旧形式留下的残余吸收进来，或者撤掉。整个过程不靠加例外、加别名、加兜底路径或者兼容代码来绕过去，也不另立一个平行的权威来源。

ETHOS 治理自己的产品仓库，和治理接入它的其他仓库，用的是同一个内核、同一套流程，这叫同构治理。区别只在配置和适配器。每个仓库在自己的配置里，声明要做哪些检查、用哪些参数、证明做到多深。适配器负责连接原生工具，比如 Git、代码托管平台和持续集成。这不是把 ETHOS 复制一份放到别处。每个仓库保留自己的业务模型、目录结构和平台习惯，ETHOS 只用同一个以证据为准的循环，来判断每一次改动。上手的头一个小时，有意只安排几件事。在仓库里运行 ethos status，看现在的事实、缺口和下一步。还没接入的仓库，先预览接入计划，预览什么都不改。确认没有冲突，也清楚出了错怎么恢复，再正式执行，因为执行要是中途被打断，可能只改了一半。

一个项目可以一点一点引入需要的结构，按自己的工作去调整，也可以交给别人或者别的 Agent 接手。按设计，它还可以整个退出。接入在设计上要做到几点：可以先预览，重复执行结果不变，已有的东西能少改就少改，而且在 ETHOS 做出第一次受治理的改动之前，都可以撤回。卸载也有设计要求：卸干净以后，不留下自动运行的钩子脚本，不留下充当权威来源的生成文件，也不留下第二套控制机制。交接或者退出之前，归属权、有用的结果和必要的证据，都要先交给负责的一方，或者存成可以恢复的形式。做完这些以后，责任已经结束的机制就该撤下，别让它变成新的负担。

再回到开头那两条线。理解给行动指出方向，实际的结果，又回过头来修正理解。ETHOS 的设计守着几条朴素的准则。一是用够用的最小模型留住含义。二是只在真正影响行动的地方做区分。三是视图只管展示，跟决定权分开，看得到，不等于有权去做。四是一个机制的责任结束了，就让它退场。照这样做的话，管线就能留下可以检验的改进，研究也能留下下一次可以追问的条件。新的问题出现时，已有的理解和学到的东西，仍然可以作为起点。项目可以接着做下去，方法也始终可以修改。
