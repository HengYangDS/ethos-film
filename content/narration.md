一个 Agent 交回来一句话：“做完了，测试全过。”这句话，到底说明了多少？它说的是哪一次提交？跑了哪些测试，在哪儿跑的？做出来的东西，是不是提需求的人真正要的？要是做错了，能不能退回去？现在，越来越多的 Agent 在替我们改代码，而且它们可以互相替换：这个会话结束了，换一个接着做。写一个改动越来越容易，难的是，能不能信得过它。听到这样一句话，人一般就两种做法：要么照单全收，要么自己从头再查一遍。照单全收，靠的是运气；从头再查，Agent 一多，就查不过来了。ETHOS 就是冲着这个难处来的。

难处有三个。第一个，是原意会走样。从前，一件事常常由一个人从头做到尾，来龙去脉都装在这个人心里。现在，一项需求从提出到落地，要经过理解、转述、交接，中间换好几个人、好几个 Agent。每转一手，原话就被一份总结顶替一次；一个会话结束，没写下来的约束也跟着没了。丢掉的，可能是一条“不能做什么”的约束，也可能是这项需求本来要带来的效益。需求哪怕写得格式齐全、挑不出毛病，目标也可能从一开始就定错了。第二个，是结论超出了证据。本地跑通了，就说全部通过；代码合进去了，就当已经发布；部署成功了，就当已经有了实际效益。其实每一步，只证明了它自己那一段。就连“测试全过”，也只说明已经写好的那些测试通过了；这些测试够不够，是另一回事。第三个，是事实还没看清，就先动了手。两个 Agent 同时改一条分支，一个照着过时的记忆写下去，另一个的工作就被覆盖了。同一个版本推到 GitLab 和 GitHub 两个平台，一边成功、一边失败，谁也说不清现在到底是什么状态；直接再试一遍，也换不来确定的答案。因为请求发出去了，不等于对方收下了；看到报错，也不等于什么都没发生。常见的办法是加流程：再加一张登记表、一本台账、一份重复的规定。可这些东西也得有人维护，时间一长就过期，互相打架，最后反倒成了新的负担。

ETHOS 走的是另一条路。这个名字是几个英文词的首字母，意思是：人和 Agent 一起打理工作，信任要建立在证据上。它想给人，也给那些可以互相替换的 Agent，一条靠得住的路：从弄清一个问题，到改动代码仓库，再到看清这次改动用起来到底怎么样。它承诺三件事：原意不丢；拿不准的地方说清楚，让人能接着处理；出了错，能恢复。多加一层治理，不在它的承诺里。这条路，靠一个很小的信任内核撑着。内核拿三样东西做输入：已经采纳的意图，刚观察到的事实，还有以前留下的存证。它按固定的规则，把这些编译成一份计划；真要写入的那一刻，再核对一遍；最后把看到了什么、判断了什么、做了什么，记成新的存证。这几样东西，寿命不一样。意图写在仓库的一份正式变更里，内核每次要用，都从那里重新编译一份。事实每次都重新去看，从不存下来当真相，因为它随时会变。计划要么执行，要么作废，都不留下，下次照样能重新编出来。内核长期留下的，只有存证：每一条都写明是谁出具的，在什么范围内成立。写明了这些，后来的人才能回头去查；出了这个范围，它就不算数。ETHOS 自己的代码，集中做内核这一件事；别的功能，先用 Git 这样现成、成熟的工具。这么一来，要理解、要验证的东西，就少得多。ETHOS 也不接管你们原有的系统。你们描述业务用的模型、自动跑检查的持续集成、运行那些 Agent 的应用、问题跟踪系统，原来是什么，现在还是什么。它在你们自己的机器上就能工作，不依赖哪一家平台；接进来的系统，也不会因此变成真相的来源。所有仓库共有的部分，归 ETHOS 统一负责；每个仓库，只管自己特有的事。这些都是它的设计目标。它自己的文档也写得明白：光有这个内核，并不能证明整条路已经走通。

ETHOS 为什么这样设计？它的产品设计契约里，写了四条判断的准则。下面用一个例子来讲；例子是假设的，只为说明道理，不是实测。有一条行情数据管线，需要时可以再跑一遍。研究员提了个要求：同一批数据再跑一遍，不能多出重复的记录；可厂商更正过的数据，一定要留下。经过两次交接，一个 Agent 写的总结只剩下一句：“按股票代码和日期去重。”照这句话去做，最该留下的那些更正，恰好会被删掉。总结能让人读得快；可它一旦顶替了原话，后面就没人再回头看原话了。第一条准则，是用刚好够用的模型，留住原意。这里说的模型，是指表达原意用的那些概念和结构。模型大了，每个人都要多懂一堆用不上的概念；小到装不下原意，原意就会在半路丢掉。做法是把意图写进一份正式变更，而且只写在这一处：要解决什么，为什么要解决，做到什么样才算解决。只写在一处，后面接手的人和 Agent，读到的都是同一份。还要拿正例和反例，来考一考对它的理解：一模一样的重复，要去掉；同一天、同一只股票的更正，要留下。那句“按股票代码和日期去重”，过不了第二个例子，更正就这样保住了。原话里相关的每一条约束，都要有个交代：要么留下，要么经授权明确排除，要么标明还没解决。理解随时可以被质疑；只有人确认过、采纳了的那部分，才按固定的规则编译成检查。编译能保证同样的输入，总会得到同样的检查，却证明不了理解本身是对的。所以对话、记忆和总结，都只是线索。

再回到那句“测试全过”。按 ETHOS 的规则，这句话要拆开来看。这一次提交，在本地做的完整核验通过了，所以这项改动可以在本地接着往下走。GitLab 和 GitHub 上的自动检查，还没出结果；版本还没发布；还没有人在用；至于有没有带来实际效益，更是还一点都没观察过。这就是第二条准则：只在影响行动的地方做区分。这几样，都是各自独立的证据：每一样通过以后，允许做的下一步都不一样。其中一样通过了，推不出另一样也通过。所以说“做完了”的时候，要讲明这一次实际确认过的是哪几样。本地核验还有一条边界：同一个账户，既能改动产生证据的程序，也能改动核对证据的程序，所以光靠本地核验，排除不了伪造。要排除伪造，得由另一个独立控制的身份重跑一遍；这一层要不要做，看风险和规定来定。一次判断的结果，也只分三种：通过、拦下、未知。必需的事实缺了，或者没法核实，结果是未知；有冲突、明确失败，或者有警告，结果是拦下。只有通过，才允许动手；未知，从来不等于可以。比如 GitLab 和 GitHub 上的检查还没出结果，这一项就是未知；没有结果，不能算作没有问题。按 ETHOS 的设计，只要不是通过，都要说清楚：发生了什么、为什么停下；证据是什么，或者缺什么事实；下一步做什么才安全，要不要人来决定。反过来，一个区分要是改变不了任何行动，ETHOS 就不去加它。多一个区分，就多一样要记着的东西；改变不了行动的区分，只会让真正要紧的那几个更难看清。

回到例子。另一个 Agent 也在干活。它记得分支还停在昨天那次提交，看板上也是一片绿灯。可从编好计划到真正写入，中间别人可能已经改过了。就在它要写入的那一刻，ETHOS 又核对了一遍：分支已经往前走了。跟计划里预想的不一样，那就什么都不写，按刚观察到的事实，重新编译计划。核对和写入，是一步完成的；写完以后，还要把结果读回来确认。一个版本推到几个平台，哪边成功、哪边失败、哪边还没推，都照实记下来。ETHOS 从不声称几个平台要么都成功，要么都失败。这就是第三条准则：把权威依据和视图分开。在 ETHOS 里，权威依据指的是一次判断可以凭借的东西：用户当下的指令，仓库里的真实内容，已经采纳的正式变更，刚观察到的事实，适用的规则，还有仍然有效的存证。摘要、看板、状态输出，还有 Agent 的汇报，都是从权威依据派生出来、给人看的视图，刚才那片绿灯也是。开头那句“做完了，测试全过”，就是这样一份汇报。视图算出来以后，情况可能又变了，视图上却看不出来：那片绿灯亮起来的时候，分支还没有往前走。视图帮人看清楚，可它不是权威依据。照着视图去改东西，就可能覆盖掉别人的工作。权威依据不明确，或者条件已经过时，判断就不能通过。

在例子里，最早那个 Agent 写了一个临时的去重脚本，还自己另开了一张进度表。等仓库自己声明的检查接住了去重这项义务，正式变更里的任务清单接住了进度，脚本和表格就该撤掉，别“先留着，以防万一”。这个脚本要是留着，过几个月可能又被人翻出来用；它算出的结果要是和仓库自己声明的检查不一样，就没人说得清该信哪一个。这就是第四条准则：义务没了，机制就退场。每一项义务，只有一个归属。对所有仓库都一样的义务，归 ETHOS 统一负责；每个仓库，只声明自己特有的检查。ETHOS 判断自己的仓库合不合格，用的也是它交给所有仓库的同一套义务。拿新做法换掉旧做法，新的不能比旧的弱。一项正式变更做到哪儿，就按哪儿收尾；没做完的留下记录，不冒充做完了。每个机制都要有人维护、有人解释，时间一长还会过期。已经没有义务的机制不撤，治理本身就成了负担。

研究员的要求，先写成一份正式变更。改动放在一条单独的工作通道里做：这条通道现在由谁持有、持有到什么时候，都有记录；改动任何一个受版本管理的文件之前，还要按当时的状态，再查一次能不能写。做到一半，一个 Agent 的会话结束了。按 ETHOS 的设计，接手的 Agent 不靠前一个的记忆。它先看刚观察到的事实，知道仓库现在是什么样子；再读正式变更，知道要做什么、做到什么样才算完；也看已有的存证，知道做过了什么、哪些核验已经通过。改完以后，在本地对这次提交做一遍完整的核验，留下存证。维护者审阅、授权以后，改动才被接受，合进受保护的开发分支。然后分别发布到每一个平台，每个平台的结果单独确认。要是推到一半断了线，顺手再推一遍？上一次也许已经成了。按 ETHOS 的设计，耗时的写入先记下要做什么，事后说清楚写进去没有、下一步做什么才安全。版本上线以后，它管不管用、有没有带来实际效益，要到实际使用里才见分晓。要说有实际效益，就要拿上线的那个版本，在它真实运行的环境里，和原来的做法比，看上一段约定的时间。从这里往后，是 ETHOS 设计要走通的一段路；它的文档也写明，这一段，和前面换 Agent 接手、断线再推那两段，都还没有完成验收。几天后，厂商在同一天，对同一只股票发了两次更正。管线只认得“原值”和“一次更正”，第二次更正，就把第一次覆盖掉了。负责观察的人把情况报了回来。按 ETHOS 的规则，三件事要分开判断。观察到的，是第一次更正不见了；推断的原因，是厂商会多次更正；提出的补救办法，是按厂商给的修订编号来区分记录。要分开，是因为推断的原因可能错，观察到的却照样成立；补救办法被否掉，也不等于问题不存在。代码出错，不一定是模型的问题，要先分清。这一次，问题出在模型上：“同一条记录”这个概念，少了一个维度。于是再走一项新的正式变更，在受影响的最小范围里修订模型，再把所有依赖它的检查重新编译一遍。不加例外，不留旁路去绕开模型，也不另立第二个真相来源。这期间，依赖这个概念的改动先停下；和它无关的工作，照常进行。“不能多出重复记录”这个目标，一个字也没有放宽。目标和标准要改，只能经授权重新对齐意图，明着改；不能为了让结果通过，就悄悄放宽。

回到开头那句：“做完了，测试全过。”按 ETHOS 的做法，这句话后面要跟着存证：说的是哪一次提交，核验了什么，哪里还没有结果，都找得到。这句话能不能信，不看是谁说的，也不看走了多少流程；要看原意是不是有一处可查，结论有没有超出证据，出了错能不能退回去。ETHOS 的标志，有三层意思。一个起点：问题在变成改动之前，先划清边界。两条路径：只在影响行动的地方分开。一道边界：证据和结论，各自守在自己的范围里。那一点朱红，是结论必须落到证据上的地方。
